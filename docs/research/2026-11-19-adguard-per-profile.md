# Per-profile filtering with AdGuard Home: what the docs already answer (2026-11-19)

Checked by Claude in a design session against primary docs, instead of running Sonnet prompts. Tags: [C] read in the project's own docs today; [S] maintainer comment in an issue or discussion; [M] inference, not confirmed.

## Findings

How AdGuard Home tells clients apart [C, [Clients](https://github.com/adguardteam/adguardhome/wiki/Clients)]: by IP address, a CIDR range, MAC address (only when AdGuard Home is also the DHCP server), or a ClientID. ClientIDs only work over encrypted DNS (DNS-over-HTTPS as `https://<host>/dns-query/<ClientID>`, DNS-over-TLS, DNS-over-QUIC).

What each client can have of its own [C, [Configuration](https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration)]: filtering on or off (`filtering_enabled`), safe search per engine (`safe_search`), blocked services with a weekly schedule (`blocked_services`), parental filter (`parental_enabled`), safe browsing, its own upstreams. Not its own blocklists: filter lists are global. Per-client blocking is done with custom rules carrying the `$client` modifier, for example `||example.org^$client='Kid'`.

Safe search [C, Configuration]: built in, per client, for Google, YouTube, Bing, DuckDuckGo, Ecosia, Yandex and Pixabay. No need to configure the providers' special DNS names by hand.

Plain-HTTP DNS-over-HTTPS [C, Configuration]: `http.doh.insecure_enabled` (since v0.107.74; before that `dns.allow_unencrypted_doh`).

Firefox can't use plain HTTP for its DNS-over-HTTPS [C, [Mozilla wiki](https://wiki.mozilla.org/Trusted_Recursive_Resolver); see also [Firefox source docs](https://firefox-source-docs.mozilla.org/networking/dns/dns-over-https-trr.html)]: `network.trr.uri` must be an `https` URL. So "each profile's Firefox points at AdGuard with its own ClientID" needs a certificate made and trusted on every box, and still covers only Firefox, not Jellyfin, Moonlight or Flatpak apps.

Matching traffic by Unix user [C, [nftables: metainformation](https://wiki.nftables.org/wiki-nftables/index.php/Matching_packet_metainformation), [nftables: NAT](https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_(NAT))]: `meta skuid <user>` matches packets from a user's sockets, and `redirect` / `dnat` in a NAT output chain can send them elsewhere on the box.

Control interface [C, [FAQ](https://github.com/adguardTeam/adGuardHome/wiki/FAQ), Configuration]: a documented HTTP API (`/control/...`). The web page and API listen on `http.address`, which can be loopback only (`127.0.0.1:<port>`). `users: []` turns the login off. No Unix-socket listener; maintainers point to a reverse proxy instead [S, [issue #3840](https://github.com/AdguardTeam/AdGuardHome/issues/3840), [discussion #3810](https://github.com/AdguardTeam/AdGuardHome/discussions/3810)].

## What this means for Hearth

- The open question is one test, not research. Every app on the box queries AdGuard from the same loopback address, so AdGuard sees one client. Whether nftables can make each Unix user's lookups arrive from a *different* loopback source address (for example 127.0.0.2 for the kid profile), so AdGuard sees separate clients, is untested [M]. About 30 minutes in a VM. Fallback: one small AdGuard Home per profile, about 60–80 MB RAM each (design doc, section 13.1).
- Loopback-only is not private. A kid's session runs on the same box, so it can reach AdGuard's API on 127.0.0.1 and turn its own filtering off. Keep AdGuard's login on, with the password held only by Hearth's system service, or let nftables allow only that service's user to reach the port [M, design point].
- Separate blocklists per profile would have to be expressed as `$client` custom rules generated by Hearth, since filter lists are global.
