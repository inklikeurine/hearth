# Hearth theming, redone from scratch (2026-11-19, v2)

This replaces an earlier theming draft that was not trusted; nothing from it was reused. Every claim below is tagged:

- [C] = confirmed: I opened the primary source (official docs, source code, the vendor's own page).
- [T] = tested: I ran it myself (Qt 6.12.0 through PySide6, headless, on a cloud box, not Hearth hardware).
- [S] = secondary source (news site or forum), because I couldn't reach the vendor's page.
- [M] = from memory, not checked.

"Claude proposes" means my recommendation. Only the list below is decided.

## What the lead decided (2026-11-19)

| Question | Decision |
|---|---|
| How to handle Kirigami's theme system | Route C. Hearth's own theme drives the shared controls and home screen directly, plus a small QML file that passes Hearth's colours to any Kirigami controls that remain |
| Fonts inside theme packs | Not allowed (changed by the lead later on 2026-11-19; first answer was yes). Hearth ships a set of open-source fonts in the OS image, and theme authors pick from those |
| How Appearance changes take effect | Preview first, then apply (Claude had proposed apply-instantly) |
| Built-in presets and default look | Scoped from scratch |
| Automatic day/night theme switching | Yes, user-settable. A day/night toggle, off by default. Off: one theme all the time. On: two dropdowns appear, one for the day theme and one for the night theme. If the chosen theme has its own light and dark modes, those fill the two dropdowns by default, unless the user has already set something in them. Switching happens at two fixed times the user sets; no sunrise/sunset, because that needs the box's location. With the toggle off, a two-mode theme shows its default mode, set by the theme's author. No playback check: Hearth shows one full-screen app at a time |

Sources I read for Hearth: the design doc, section 9 (theming layers) and section 10 (settings pages). I read these through the project's GitHub sync; I couldn't clone the repo here because access was denied.

## Answer in brief

1. Theming is cheap now and expensive later, and the Bigscreen code shows why.
   - Bigscreen's colours come from KDE's desktop colour scheme. Its Plasma look-and-feel package sets `ColorScheme=BreezeDark` [C].
   - Remove Plasma and the colours change. Kirigami then uses whatever the chosen Qt Quick Controls style supplies, or its own built-in palette if the style supplies nothing [C, Kirigami source]. So Hearth has to own the colours from day one either way.
2. The job is smaller than it looks.
   - Bigscreen's QML uses only 7 colour roles (in 4 colour sets), the default font, and 13 size/time names from Kirigami [C, my counts below].
   - In the shared controls and home screen, which Hearth keeps, that's 362 references to point at Hearth's own theme. Most of the rest sits in settings pages and shell files that the design doc already plans to rebuild.
3. Design tokens work, and I ran them [T]. One JSON file restyled a small QML home screen: dark, high contrast with large text, and a hostile file. The hostile file had nothing executed. Out-of-range values were clamped and unreadable colours refused.
   - The demo also caught three real bugs that theming causes: text spilling out of tiles, a button disappearing in the high-contrast theme, and a missing font being silently swapped. All three are fixed in the demo and turned into rules below.
4. A theme pack can be data-only. "Data" still needs care:
   - Qt's SVG renderer loads image files that an SVG links to [C, Qt source].
   - A font-parsing bug in FreeType (the library that reads font files) was exploited in real attacks in 2025 [S].
   - That risk is why the lead ruled out fonts in packs. For images and sounds, Claude proposes: re-encode them at import and rasterise SVGs in a locked-down helper (section 5).

## 2. Design tokens, with a working example

What it is. A *design token* is one named setting for how the interface looks, such as `accent = #4F8CFF` or `focusIn = 150 ms`. All tokens live in one data file. Screens never contain a raw colour, size or time; they ask the theme for one by name. Change the file and every screen changes. Kodi's `defaults.xml` above is a real example.

How it works. A loader (C++ in Hearth) reads the theme file, checks every value against a fixed list of allowed names, types and ranges, refuses unreadable colour pairs, and fills a QML object of typed properties with built-in defaults. Screens bind to it (`color: t.accent`). Helpers turn design units into pixels, apply the Text Size setting to text, and scale every animation by one motion-speed number, so Reduced Motion is a single value. A theme that changes only a few values falls back to the defaults for the rest, as Kodi's does.

What the demo showed [T]: one file restyled a small home screen as dark, and as high contrast with larger text. A hostile file had nothing executed: script-like values were refused, out-of-range sizes and speeds were clamped, and an unreadable colour pair (1.01:1) was refused. The demo's colours and sizes are placeholders and mean nothing for Hearth's look.

Bugs the demo caught. Each is now a rule for Hearth:
1. Text spilled out of its tile at large sizes. In the first hostile run, body text of 64 made "Moonlight" run into the next tile.
   - Fix: every text has a width and `elide`.
   - Fix: the loader has a minimum and maximum text size. The demo used 28–42 du; the real range waits on scoping the text-size floor.
2. A button vanished in the high-contrast theme. Its fill (`#000000`) matched the background.
   - Fix: an `outline` colour and `border.width` token, which high-contrast themes turn on.
   - The loader now warns when a control colour is too close to the background.
   - That warning also fired for the placeholder dark colours (`surface1` on `bg` is 1.09:1). Whatever presets get scoped need the same check.
3. The font was silently swapped. I asked for "Noto Sans", which isn't installed on the test box. Qt used Inter instead and said nothing [T].
   - Fix: the loader checks that the font family exists, and CI does the same for built-in themes.

QML facts I checked [T unless marked]:
- Setting a colour in JavaScript (`Component.onCompleted: color = …`) breaks the link to the theme. After a theme switch, a bound rectangle turned white; the assigned one stayed dark.
   - Bigscreen has no such assignments today [C, grep].
   - Rule for new code: use bindings only.
- A delegate inside a `Repeater` loses `modelData` once the component has a `required property`, unless the delegate declares `required property string modelData` too. I hit this error myself.
- A property named `onAccent` works fine in Qt 6.12. Naming tokens `onSomething` is not a problem. The old doc's claim was wrong.
- QML's built-in `XMLHttpRequest` can't read local files unless `QML_XHR_ALLOW_FILE_READ=1`, and Qt says to use that "only if you know that the application runs trusted QML and JavaScript code" [C, [Qt docs](https://doc.qt.io/qt-6/qml-qtqml-xmlhttprequest.html)]. So the C++ side reads theme files, never QML.

The demo (about 340 lines including the theme files) was a throwaway teaching aid and is not kept in the repo; its findings are the rules above and in section 4.

How it behaves (Claude proposes):
- Two copies of the theme. Left/Right only changes the *preview* copy, shown in the right-hand box. The controls on the left stay in the applied look the whole time, so a bad choice can never make the screen you're using unreadable. This needs `ThemeData` to be a reusable type with two instances (live and preview), as in the demo.
- Apply copies the preview into the live theme. Undo changes copies the live theme back into the preview. Back with unapplied changes asks Apply / Discard / Stay.
- Imported themes also get the 15-second "Keep this theme?" check after Apply, because the preview box can't show every screen.
- No free colour picker. About 8 curated accents, each checked for 3:1 against the background and the tiles. The design doc already says colour pickers are miserable with a remote.
- Every row is a short list of named steps, not a free slider. Named steps are faster with a remote and each one can be tested.
- Changing anything on a preset shows "Preset name (changed)", and Reset to preset is always reachable.
- Way out if the screen becomes unreadable: hold Back for 5 s anywhere to switch to a built-in safe theme. This is my idea, not something I found in another product.
- Contrast is shown, not hidden. The readout uses the WCAG floors: 4.5:1 for text, 3:1 for the focus ring. The numbers depend on the scoped presets.

Auto day/night (decided by the lead):
- A day/night toggle, off by default. Off means one theme all the time.
- Turning it on shows two dropdowns: Day theme and Night theme.
- If the theme in use has its own light and dark modes, its light mode fills the Day dropdown and its dark mode fills the Night dropdown, unless the user has already set something there. So a theme with both modes works with no extra setup, and the user can still mix themes.
- No check for video playback. Hearth shows one full-screen app at a time, so the switch isn't visible then. The only exception is an overlay opened over an app, which would just open in the new colours.

## 4. Mistakes that make theming painful later, and what Bigscreen does today

Where I looked:
- KDE `plasma-bigscreen`, GitHub mirror, commit `5c3b801` (2026-11-19): 110 QML files.
- Kirigami, commit `b43d533`.
- Counts are exact matches of the patterns given, so they are exact for those patterns, not for every possible spelling.

| # | Mistake | Seen in Bigscreen [C] | Avoid it by |
|---|---|---|---|
| 1 | Colours written straight into screens | 2 hex colours, 12 named colours (`color: "white"` three times in the home clock, `Clock.qml`, so the clock would stay white on a light theme), 21 `Qt.rgba` colours | A CI check that fails any colour outside the theme files |
| 2 | Colours worked out in code | `DelegateBackground.qml` decides "is this a light theme?" from background lightness > 0.5, darkens borders with `Qt.darker(…,1.2)`, builds the focus border from hue maths, and darkens shadows by 1.7 | Make each of these its own token (`focusFill`, `focusBorder`, `outline`, `shadow`) so a theme author controls it |
| 3 | Focus drawn separately in many places | 9 files style their own focus. Examples: 2 px border in `DelegateBackground.qml`, `smallSpacing` (4 px) border in `AbstractDelegate.qml`, 1.06× scale in the home `IconDelegate.qml` | One shared `FocusFrame` that reads `focusStyle`, `ringWidth` and `focusScale`. A Focus Style setting then means changing one file, not nine |
| 4 | Text sizes outside the scale | `Units.qml` hard-codes body 18 px and headings 22 px; 17 more literal `pixelSize` values (18, 28, 30, 32) | Every text size through `fontPx()`. The minimum text size for TV viewing is part of the preset scoping |
| 5 | Animation times outside one switch | 28 literal `duration:` values in 13 files, plus 41 Kirigami duration names | Every duration through `ms()`, so Reduced Motion is one number |
| 6 | Look depends on the desktop it runs in | The look-and-feel defaults set `ColorScheme=BreezeDark` and `widgetStyle=Breeze` in KDE's global settings | Without Plasma, Kirigami picks a platform plugin by Qt Quick Controls style name, else `BasicTheme` [C, `platformtheme.cpp`]. Hearth must supply its own colours or they quietly change |
| 7 | "Theme" packages that contain code | Bigscreen's look-and-feel package ships `Splash.qml`, a QML program | Keep Hearth's packs data-only (section 5). Layout skins stay developer mode only, as the design doc says |
| 8 | Sounds and icons outside the theme | Sounds are fixed paths `sounds/plasma-bigscreen/clicked.wav` and `moving.wav`; about 44 icons referenced by fixed names | Give sounds and a fixed list of icons named slots in the theme |
| 9 | Text that can't grow | (found in the demo) | Every text has a width and `elide`; test each screen at 150 % text |
| 10 | Controls that vanish on some backgrounds | (found in the demo) | Outline token, plus a check for how close control colours are to the background |
| 11 | Missing fonts swapped silently | (found in the demo) | Check the family exists before using it; fall back to an image font on purpose, with a warning |
| 12 | Only Hearth's own screens follow the theme | n/a | Publish the standard desktop appearance settings (below) so apps that read them follow along. Feed the same tokens to the Firefox extension as CSS variables for focus and overlay colours, as design doc §9 promises |

About #12. The freedesktop "Settings" portal (the standard way Linux apps, including Flatpaks, ask the system about its settings) defines four standard appearance keys [C, [portal spec](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html)]:
- `color-scheme`: no preference, dark, or light.
- `accent-color`.
- `contrast`: normal or higher.
- `reduced-motion`.

These map one-to-one onto Hearth tokens. Whether Jellyfin and Moonlight honour them is untested.

The Kirigami question. Bigscreen uses `Kirigami.Theme` 195 times and `Kirigami.Units` 486 times. Kirigami is KDE's QML toolkit, and it runs outside Plasma.

- Colours: 7 roles, mostly `backgroundColor` 51, `highlightColor` 30, `textColor` 25 and `disabledTextColor` 20, used inside 4 colour sets (Window, View, Button, Complementary), plus `defaultFont`.
- Units: `gridUnit` 205, `smallSpacing` 103, `largeSpacing` 80, `longDuration` 35, icon sizes and a few others.

By folder (Theme + Units references):

| Folder | Theme | Units | Hearth plan |
|---|---|---|---|
| components (shared controls) | 25 | 109 | keep |
| containments (home screen) | 70 | 158 | keep |
| webapp-viewer | 4 | 8 | drop (uses Qt WebEngine; see conflicts) |
| uvcviewer (camera/console input viewer) | 0 | 3 | keep or drop, undecided |
| kcms (settings pages), shell, settingsapp | 94 | 193 | rebuilt without Plasma (design doc §10) |

Two facts from Kirigami's source decide the options [C]:
- Without a platform plugin, Kirigami's `BasicTheme` loads a `Theme.qml` from the current Qt Quick Controls style folder. That file is a plain QML `Kirigami.BasicThemeDefinition` listing every colour. Kirigami's own Material style does exactly this. So Kirigami's colours can be driven from Hearth tokens with one QML file and no C++.
- `Kirigami.Units` values are read-only from QML (no WRITE in the property declarations). Its defaults are `gridUnit` 18, `smallSpacing` 4, `largeSpacing` 8, durations 400 / 200 / 100 ms and corner radius 5. Changing them needs a C++ Kirigami platform plugin.

| Option | What it is | Cost / risk |
|---|---|---|
| C. Both (Claude's pick) | Shared controls and the home screen use Hearth `Theme` directly (362 references, a mechanical swap through a short mapping table). Ship a Hearth `Theme.qml` for Kirigami so any Kirigami control left over still gets Hearth colours | Most of the swap happens anyway when screens are touched. The bridge file is small but installs into Kirigami's style folder, and the exact path is untested |
| A. Replace only | Swap everything to Hearth `Theme`, no bridge | Any Kirigami control we keep (icons, form layouts) shows Kirigami's built-in colours |
| B. Bridge only | Keep Kirigami names everywhere; feed colours via `Theme.qml` and units via a C++ platform plugin | No QML edits, but motion speed, focus style and text scale aren't Kirigami concepts, so they'd still need Hearth's own theme. The plugin uses Kirigami internals that can change between releases |

Hard to undo: whichever name screens use (`Theme.` or `Kirigami.Theme.`) gets copied into every new screen. Pick before the first new screen is written.

## 5. Theme packs that can only contain data

```
cozy-amber.hearth-theme            a .zip (a plain folder while you're making one)
├── theme.json        required. Tokens + meta + file slots. ≤ 64 KB          
├── preview.png       required. 640×360 picture for the theme picker         
├── LICENSE.txt       required. Author and licence for every file in the pack
├── wallpaper/home.jpg            optional                                   
├── sounds/move.ogg select.ogg back.ogg error.ogg    optional, ≤ 2 s each    
├── icons/<name>.png              optional, names from a fixed Hearth list   
```

The on-screen keyboard is drawn by Hearth from the same tokens, so a pack restyles it without extra files. Optional key-click sound slots can be added. A theme may define a light mode and a dark mode in `theme.json`, and marks one as its default. `theme.json` names files only through fixed slots, for example `"files": { "wallpaper": "wallpaper/home.jpg" }`. It holds no URLs, paths outside the pack, or free-form names.

What I confirmed about the risks:
- Zip "path traversal". Entry names like `../../x` can overwrite files outside the target folder. The standard fix is to check each output path stays inside the target after resolving it [C, [Android security guide](https://developer.android.com/privacy-and-security/risks/zip-path-traversal)].
- SVG.
   - Qt SVG implements the static features of SVG 1.2 Tiny, and `libQt6Svg` links only Qt Core, Gui and DBus, with no script engine [C, Qt SVG source `svgextensions.qdoc`; T, linker check].
   - However, its `<image href="…">` handling loads a local image file by path, relative or absolute [C, `qsvghandler.cpp` `createImageNode`]. A pack's SVG icon could pull a picture from elsewhere on the box onto the screen. Nothing runs and nothing leaves the box, but it isn't "data only".
   - Qt 6.7+ has a `Tiny12FeaturesOnly` option and Qt 6.9+ can turn off animations [C, `qsvgglobal.qdoc`].
- Fonts. CVE-2025-27363, an out-of-bounds write in FreeType's TrueType GX/variable-font parsing that can lead to code execution, "may have been exploited in the wild" per Meta, and Google patched it in Android as exploited [S, [The Hacker News](https://thehackernews.com/2025/03/meta-warns-of-freetype-vulnerability.html), [OpenCVE](https://app.opencve.io/cve/CVE-2025-27363)]. I couldn't load CISA's catalogue page to confirm it is listed there.
- Precedent for data-only themes. A Firefox static theme is `manifest.json` plus images, and Mozilla says theme and extension functionality can't share one package [C, [Extension Workshop](https://extensionworkshop.com/documentation/themes/static-themes/)].

Importer rules (Claude proposes):
1. Unpack in a separate, locked-down helper process, not the UI. The exact sandbox (for example a systemd service with no network and only the target folder writable) still needs researching.
2. Refuse the whole pack for:
   - any absolute path, `..`, symlink or duplicate name
   - nested archives
   - more than about 64 files, or more than about 20 MB in total
3. Accept files only into known slots. Check the type by content, not by file name.
4. Re-encode everything. Decode each image or sound with size limits and write a fresh PNG/JPEG/OGG made by Hearth, so the UI only ever opens files Hearth wrote. Turn SVG icons into PNG at import, so `<image href>` never gets a chance.
5. `theme.json` goes through the same checker as the demo: fixed names, types, ranges, colour format, contrast floor, and a font family from the list shipped in the OS image.
6. Fonts: not allowed in packs (lead, 2026-11-19). A theme names one of the open-source font families shipped in the OS image, so no font file ever comes from outside. Letters a family lacks (other languages) fall back to other image fonts.
7. Install into a writable themes folder outside the read-only system image. Never onto a QML import path, and never loaded with `Loader` or `Qt.createComponent`.
8. No network. Sharing means a file on USB or, later, a file sent from the phone through KDE Connect. I didn't check how KDE Connect's file sharing would hand a file to Hearth.

## What's unconfirmed or needs real hardware

- Theme-switch speed on a 4 GB box with 7th-gen Intel, Raven Ridge-class AMD and an NVIDIA card. A switch re-checks every binding on screen. Untested.
- The Kirigami bridge. Where exactly a Hearth `Theme.qml` must be installed and whether Bigscreen's controls pick it up without Plasma. Mechanism read in source; not run.
- Whether Jellyfin, Moonlight and Firefox follow the portal's dark/light, accent, contrast and reduced-motion settings.
- Steam Big Art Mode and screensaver menu paths come from news sites quoting Valve, not Valve's own page.
- Remote steps for Projectivy, and the tvOS Increase Contrast and Reduce Motion pages, were not read.
- The demo ran on Qt 6.12, headless on a cloud machine, at 1080p only.
- Bigscreen counts are exact for the search patterns I used, not proof that nothing else is hard-coded.

## Conflicts with ground rules or docs

- Local only vs the design doc's "share online". Any online theme gallery would be a named, switchable network connection. Claude proposes USB (and later phone) import only for 1.0.
- Borrow with credit. Kodi's Estuary is GPL-2.0 code with CC-BY-SA-4.0 art, so ideas are fine and code reuse would need care. Projectivy shows no licence I could find, so take ideas only. Kirigami is LGPL, Bigscreen GPL/LGPL.
- AI policies. I only read upstream code. Nothing goes to KDE, Kodi or Qt, so their AI policies weren't checked.
- No Chromium in our own development. Bigscreen's `webapp-viewer` imports `QtWebEngine` (`WebApp.qml`, `WebView.qml`) [C]. Qt WebEngine is built on Chromium [M; the Qt docs page I opened didn't say so]. Hearth's fork should drop that folder; Hearth's web apps run in Firefox kiosk.

# One-page summary for the design chat

Theming goes in before any new screens. Removing Plasma already forces Hearth to supply its own colours: without Plasma's settings, Kirigami takes them from the Qt style or its own built-in palette [C]. Bigscreen's shared controls and home screen need 362 references switched to Hearth's theme, through a short mapping [C]. A working demo shows one JSON file restyling a QML screen and refusing a hostile file [T].

The lead decided (2026-11-19):
1. Kirigami: route C. Hearth's theme drives the shared controls and home screen, plus a small QML-only bridge so any remaining Kirigami controls get Hearth's colours.
2. No fonts in theme packs. Open-source fonts ship in the OS image for theme authors to pick from (changed later the same day; the first answer was yes).
3. Appearance changes: preview first, then apply.
4. The preset set and default look get scoped from scratch.
5. Automatic day/night switching: yes, user-settable. A toggle, off by default. On shows Day theme and Night theme dropdowns, pre-filled from the theme's own light and dark modes unless the user has set them. Fixed switch times set by the user. Toggle off: a two-mode theme shows its author's default mode. No playback check.

Claude proposes (not decided):
1. Token set: colours (including outline, focus fill and border, shadow), type sizes, spacing, radius, motion speed (0 = off), focus style, ring width and scale, sound and icon slots, and a font family from the image's list. Values come from the scoping work.
2. Appearance screen:
   - The controls stay in the applied look while a separate preview box shows the candidate.
   - Apply, Undo, and an Apply/Discard/Stay prompt when you press Back with unapplied changes.
   - 15-second "Keep this theme?" after applying an imported theme.
   - Hold Back 5 s anywhere for a built-in safe theme.
   - Curated accents, named steps instead of sliders, and a live contrast readout using the WCAG floors.
3. Packs:
   - A zip with `theme.json`, a preview image, a licence file, and optional wallpaper, sounds and icons in fixed slots.
   - A separate locked-down importer re-encodes images and sounds and turns SVGs into PNGs.
   - No URLs; USB import in 1.0.
4. Fork order:
   1. Hearth theme, loader and automatic checks (literal colours, contrast, font exists, 150 % text screenshots)
   2. shared controls and one shared focus highlight
   3. home screen
   4. Kirigami bridge
   5. new screens
5. Publish the standard Linux appearance settings (dark/light, accent colour, contrast, reduced motion) through the desktop portal, so Flatpak apps can follow.

Confirmed: the Kodi, Projectivy, tvOS and webOS settings; Bigscreen and Kirigami source facts; Qt SVG and XHR behaviour; portal keys; the zip-traversal fix; Firefox static themes.
Tested: the token demo and its three bug finds; that setting a colour from code breaks the theme link; that `onSomething` names are fine.
Second-hand: Steam's Big Art Mode and screensaver details; reports that the FreeType font bug was used in real attacks.
Untested or unresearched:

- the Kirigami bridge install path
- whether apps honour the portal settings
